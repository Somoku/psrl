## 1. TL;DR

瓶颈不是链路、不是调度、不是提交次数，而是**单次传输里的 descriptor 数量**。
它的来源是一处纯粹的布局巧合，不是架构必然：

> **row-parallel 层（`o_proj` / `down_proj`）的分片轴正好是内层维，
> 于是「按 LCM mesh 再切一刀」就把连续张量切成了 `hidden_size` 行。**

根因算术完全闭合（Qwen3-8B，gen TP=2 / train TP=4）：

```
144 strided 分片 = 36 层 × 2 个 row-parallel 键 × 2 个 mesh cell
每分片 4096 行   = hidden_size = 恰好是「没有被分片的那一维」
```

三条出路，按「改动面 / 收益 / 风险」排序：

| | 方案 | descriptor | 改动面 | 适用性 |
|---|---|---|---|---|
| **P1** | 输入维对齐（gen TP 的输入维分片数 == train） | 589,824 → **144** | 配置校验 + 一处 planner 判定 | 仅当并行度可选 |
| **P2** | 连续落地缓冲 + 本地 scatter | 589,824 → **144** | 执行层，需生命周期管理 | **通用，推荐** |
| **P3** | 维持现状，关闭扩散 | 不变 | 已完成（`peer_diffusion=False`） | 兜底 |

P2 是真正的解，P1 是它的特例，P3 是在 P2 落地前的默认。

## 2. 根因：一处布局巧合，不是架构必然

### 2.1 为什么只有 row-parallel 层出问题

vLLM 的权重是 `[out_features, in_features]`，内存按行主序排列，
**所以 `in_features` 是内层（连续）维**。

| 层类型 | 分片轴 | 切完之后 |
|---|---|---|
| column-parallel（`qkv_proj`, `gate_up_proj`） | `out_features`（外层维） | **仍然连续** —— 切的是整行的集合 |
| **row-parallel**（`o_proj`, `down_proj`） | **`in_features`（内层维）** | **变成 strided** —— 每行被切断，行间产生间隙 |

这就是为什么 gen 侧是 144 个 strided 分片而 train 侧只有 54 个：
**同一个模型、同一套代码，差别只在哪一维被切。**

### 2.2 为什么行数恰好是 4096

`o_proj` 是 `[4096, 4096]`，`down_proj` 是 `[4096, 12288]`，两者的 `out_features`
都是 `hidden_size = 4096`。切内层维时，**外层维的大小就是行数**：

```
行数 = out_features = hidden_size = 4096
```

于是 descriptor 数 **与模型宽度同阶**。这条值得单独强调，因为它决定了问题的走向：
**模型越大，这个数越大。** 70B 级模型 `hidden_size = 8192`，descriptor 数翻倍；
而每 descriptor 约 2.1–4 µs 的成本不随之下降。**这不是一个会被硬件进步解决的问题。**

### 2.3 为什么「必须重分片」而不是「直接读本地张量」

train TP=4、gen TP=2 时，输入维的 LCM mesh 是 4，gen 每键要持有 2 个 mesh cell。
gen 的本地张量 `[4096, 2048]` **本身是连续的**，但它要对应 train 两个 rank 的数据，
所以必须按 mesh 再切成两份 `[4096, 1024]` —— **切这一刀的瞬间就 strided 了**。

实测确认（`describe_shard`）：

```
train rank 本地张量  [4096, 1024] 整体  -> rows=1     连续，1 个 descriptor
gen  mesh cell      [4096, 1024] 切片  -> rows=4096   strided，4096 个 descriptor
```

**同样的形状、同样的字节数，一个是 1 个 descriptor，一个是 4096 个。**
差别只在它是「一块独立张量」还是「一块更大张量的列切片」。

## 3. P1：输入维对齐

### 3.1 做什么

若 gen 与 train 在**输入维**上的分片数相同，就不存在 LCM 重分片，
gen 的本地张量整体就是一个 mesh cell —— 连续，1 个 descriptor。

实测确认：`gen 本地张量整体即为 mesh cell -> rows=1`。

注意要求的是**输入维分片数相同**，不是「TP 完全相同」：
column-parallel 层切外层维，怎么切都连续，不参与这个约束。

### 3.2 代价与边界

- **这是一条配置约束，不是优化。** 它把 gen 的并行度和 train 绑在一起，
  而 rollout 的 TP 本来是按**推理吞吐**选的（KV cache 容量、batch 并发），
  不是按权重传输选的。拿推理性能换传输性能，通常不划算。
- 因此 P1 **不能作为主方案**，只能作为：
  (a) 配置校验里的一条提示（「当前并行度会产生 N 个 strided 分片，
      预计 descriptor 成本 X ms；输入维对齐可消除」）；
  (b) P2 的快路径——对齐时 P2 自动退化为零拷贝，不需要落地缓冲。

### 3.3 落地项

| # | 项 | 说明 |
|---|---|---|
| P1-a | 握手期统计并上报 strided 分片数与预估 descriptor 成本 | 让这件事**可见**。现在它完全沉默，是我自己花了三轮实测才定位到的 |
| P1-b | 配置校验打印输入维对齐建议 | 提示而非拒绝：这是性能取舍，不是正确性问题 |

## 4. P2：连续落地缓冲 + 本地 scatter（推荐）

### 4.1 核心思路

把「网络传输的布局」和「参数的布局」解耦：

```
                    1 个 descriptor                  本地 D2D scatter
train rank 连续分片 ──────────────▶ gen 连续落地缓冲 ──────────────▶ gen strided 参数
                      (走网络)                        (不走网络)
```

RDMA 永远只搬**连续块**，strided 的那一刀留在本地用一次 GPU 拷贝完成。

实测确认：扁平落地缓冲 `rows=1`，1 个 descriptor。

### 4.2 为什么这是对的取舍

| | 现状 | P2 |
|---|---|---|
| descriptor（gen 每 client） | 589,824 | **144** |
| descriptor 时间 | 1.24 s | **0.30 ms** |
| 额外本地拷贝 | 0 | ~5 ms（8 GB @ 1.5 TB/s） |
| 额外显存 | 0 | `O(chunk)`，见 §4.4 |

**用约 5 ms 的本地带宽换掉约 1.24 s 的 descriptor 成本。**
这个比例不是调优余量，是两个数量级——而且它是**结构性**的，
因为本地拷贝的成本随字节线性、descriptor 成本随模型宽度线性，
后者在大模型上只会更糟。

### 4.3 关键发现：staging 缓冲其实是可注册、可寻址的

我在 D1 收尾时写过「staging 分片没有 remote descriptor，所以不能作为读源」。
**这个说法需要修正**：落地缓冲**确实被注册**，descriptor 也确实被序列化并交换
（`client.py` 写入 `temp_desc_bytes_list`，并通过 `_all_temp_mappings` 分发）。
`client_read` 拒绝它，只是因为那条路径只查 `desc_bytes_list`。

**真正的障碍不是可寻址性，而是生命周期**：槽位按
`i % max_pinned_temp_memory_slots` **复用**，所以缓冲里的内容是瞬态的——
follower 去读时，designate 的那块槽位可能已经被另一个分片覆盖了。

这把 P2 与扩散的关系从「互斥」改判为「需要生命周期管理」，
而生命周期管理正是 §4.4 已经为 FP8 cast 产物设计过的机制。

### 4.4 生命周期：复用 plan 已有的答案

落地缓冲和 FP8 的 cast 产物是**同一类字节**——都不是参数本身，
都要活到「所有计划中的读者读完」为止。所以规则可以直接搬：

```
落地缓冲槽位可回收 ⟺ planned_readers(chunk) 全部完成对该 chunk 的读
```

`planned_readers` 在握手期就是已知的有限集合（§3.5 的三阶段 plan），
完成检测复用 `GroupCompletionTracker` 与 `chunk_notify.py` 的逐 chunk 信号
（已落地、已集群验证）。**不需要新机制。**

槽位数 = 流水级数，与模型大小无关：取 `D = 3`（一级在落地、一级在被读、
一级在 scatter），常驻显存 `3 × chunk_bytes`。

### 4.5 scatter 必须与传输重叠，否则只是换了个地方等

落地与 scatter 是**不同资源**（RDMA vs GPU copy engine），天然可重叠：
chunk `i` 在 scatter 时 chunk `i+1` 在落地。
这正是 `chunk_pipeline.py` 已经在做的事——
**P2 不需要新的流水，它需要的流水已经存在且已验证**。

这一点是 D1 工作的真正价值所在：之前流水「正确但无收益」，
因为它重叠的是 descriptor 成本（不可压缩）；
P2 之后它重叠的是本地拷贝（真实工作），流水才第一次有东西可隐藏。

### 4.6 落地项

| # | 项 | 依赖 | 说明 |
|---|---|---|---|
| P2-a | 落地缓冲池 + 按 chunk 分配槽位 | — | 复用现有 pinned slot 机制，改按 chunk 而非按 (key,shard) 分配 |
| P2-b | 本地 scatter kernel | P2-a | `landing.view(rows, row_bytes) -> param[:, cell]`，一次 `copy_` 即可 |
| P2-c | 槽位生命周期挂到 `planned_readers` | P2-a、`chunk_notify` | §3.4；**必须运行时断言**，提前回收会读到被覆盖的字节且不报错 |
| P2-d | 对齐时退化为零拷贝 | P2-a | 输入维对齐（P1）时 `rows=1`，直接原地注册，不走落地缓冲 |
| P2-e | scatter 与落地重叠 | P2-b、`chunk_pipeline` | 流水已存在，接上即可 |
| P2-f | 扩散与 P2 共存 | P2-c | 落地缓冲可作读源，前提是生命周期覆盖 follower 的读 |

## 5. 当前问题能否解决：分三层回答

### 5.1 能解决的（有实测依据）

- **descriptor 膨胀**：589,824 → 144，这是算术而非估计。
- **扩散净亏的根因**：亏损来自 designate 被迫原地注册（每分片 4096 个 descriptor）。
  P2 通过让 rollout 成为纯目的地绕开了它 —— 注意是**绕开**而非「两者兼得」：
  扩散与 staging 互斥，实测 staging 侧快 4.07×（§10.3）。
- **一处必须更正的前提**：初稿据单 NIC 24.50 GB/s 推出「同节点快 14×」，
  并以此论证扩散。**P2 的实测否证了它**：每节点聚合入口约 103 GB/s
  （约 4 条 NIC 并行），所以真实差距是 **3.3×**，不是 14×（§10.3）。

### 5.2 不确定的（必须实测，不能推演）

- ~~**scatter 的真实带宽。**~~ **S0 已实测，门禁通过，余量远超预期**
  （`bench_strided_scatter.py`，H20 单卡）：

  | 形状 | 载荷 | scatter | 带宽 | 相对扁平拷贝 | 替代的 descriptor 成本 | 倍数 |
  |---|---|---|---|---|---|---|
  | `o_proj` cell (4096×1024) | 8 MiB | 0.023 ms | 369.9 GB/s | 1.9× | 8.602 ms | **379×** |
  | `down_proj` cell (4096×3072) | 24 MiB | 0.058 ms | 433.8 GB/s | 2.5× | 8.602 ms | **148×** |
  | `o_proj` 70B (8192×2048) | 32 MiB | 0.078 ms | 428.6 GB/s | 2.6× | 17.203 ms | **220×** |

  两条结论值得单列：
  1. **strided 写入只比扁平拷贝慢 1.9–2.6×**，不是我担心的「对 HBM 不友好」。
     370–434 GB/s 的有效带宽意味着 `copy_` 在这种形状下已经足够好，
     **不需要自定义 kernel**（P2-b 因此从「写 kernel」降级为「一行 `copy_`」）。
  2. **倍数随模型增大而改善**（70B 的 8192 行：220× vs 4096 行的 148×），
     因为 descriptor 成本随行数线性增长，而 scatter 成本随字节增长且带宽不变。
     **这个方案在大模型上更有优势，而不是更差。**

- **落地缓冲的显存与 KV cache 的冲突。** `3 × chunk_bytes` 账面很小，
  但 vLLM 的 `gpu_memory_utilization` 是预先切走的，新增常驻显存要从
  KV cache 里挤——需要显式预留而非 best-effort。
- **大 MoE 下是否仍成立。** Qwen3-8B 的 row-parallel 键只有 72 个；
  MoE 模型的 `down_proj` 是 per-expert 的，键数与分片数都会上一个量级。
  注意 S0 的第二条结论说明**这更可能是优势而非风险**，但仍需实测。

### 5.3 解决不了的（边界要说清）

- **这不改变 descriptor 成本本身**，只是让每次传输只用 1 个。
  若将来出现「必须 strided 传输」的场景（例如不能分配落地缓冲的极端显存压力），
  成本会回来。
- **P2 不省字节，只省 descriptor。** 跨节点带宽仍是瓶颈（实测每节点聚合约
  103 GB/s），所以 §3.5 的去冗余规划与 FP8 wire 仍然各自必要。

## 6. 推进顺序与判据

**先做最便宜的否证实验，再投入实现**——这是本轮最该吸取的教训：
我有三个假设是靠 25 分钟的集群跑否证的，其中两个本可以用几分钟的微基准否证。

| 阶段 | 内容 | 成本 | 判据 |
|---|---|---|---|
| ~~**S0**~~ | ~~微基准：strided scatter 的真实带宽~~ | 单卡，分钟级 | ✅ **已通过，最差 148× 最好 379×**（§4.2） |
| ~~S1~~ | ~~可见性：上报 descriptor 数与预估成本~~ | 纯 CPU | ✅ 日志出现 `589824 descriptor(s), worst shard 4096 rows, est. submit cost 1238.6ms` |
| ~~S2~~ | ~~落地缓冲 + scatter + 生命周期~~ | 中 | ✅ **机制本已存在**（见下），只需让读侧选用 |
| ~~S3~~ | ~~配置化 + 两侧一致~~ | 小 | ✅ `shards_must_be_readable` / `peer_diffusion`，server 与 client 读同一份 |
| ~~S4~~ | ~~5 节点同轮 A/B~~ | 一轮 | ✅ **0.619s，3.68× 于最好基线**，16/16 × 399/399 |
| ~~S5~~ | ~~扩散与 P2 共存~~ | 一轮（零代码） | ✅ **已量化并否决**：扩散 2.519s vs P2 0.619s = 慢 4.07×（§10.3） |

**S2 的一处重要发现：落地 + scatter 的机制原本就完整存在。**
`client.py` 的 staging 路径已经做了「连续落地缓冲 → 一个 descriptor → 本地
`original_tensor.data.copy_(contiguous_tensor)`」，两侧的槽位等待与 event cache 也都在。
**缺的只是「读侧愿意选它」**——A2 的原地注册无条件优先，于是这条路从未被走过
（历次实测 `temp_desc_slice_map=0`）。
所以 S2 的实现量远小于预期：加一个行数预算与一个可读性判定即可。

**槽位复用不是问题，已算过。** 4 个槽位服务 72 个分片意味着串行 18 深，
但每次 staged 传输只需约 4 µs 提交 + 0.058 ms scatter，
18 深串行约 1 ms —— 对比原地的 1239 ms。**不需要扩大槽位池。**

**S0 的门禁价值**：它本可以否决整个方案，只花了几分钟。
对照本轮用三次 25 分钟集群跑去否证的三个假设，**这个顺序本身就是结论**。
S0 还顺带改小了实现：`copy_` 已够快（370–434 GB/s），**不需要自定义 kernel**。

## 7. 验证要求（继承 D1 的教训）

1. **任何性能结论必须来自分解计时，不是总耗时。** 本轮四个假设里三个
   错在从总量反推。`pull_pipelined` 的五段计时与 `read_phase_us`
   的四段计时要继续保留，P2 再加一段 `scatter`。
2. **A/B 必须同轮。** 跨轮比较不可信：集群状态、模型加载顺序、NIC 争用都在动。
3. **集群结论必须带 `[PASS] all 5 nodes import this tree`。** 没有这行的日志不可用。
4. **生命周期必须有反例测试。** 提前回收槽位会让读者读到被覆盖的字节，
   而那次读**会成功**——和 FP8 的静默失败同类，必须用断言而非期待。
5. **scatter 必须有按位 oracle。** 对比「P2 落地+scatter」与「直接 strided 传输」
   的最终参数，要求按位相等。

## 8. 与现有设计的关系

- **A2（Nx5 strided descriptor）的定位需要修正。** 它解决的是元数据体积
  （descriptor 列表 16384→1）与 prep 时间，**不含提交时间**
  （§3.6.3 的 GPU 实测已证伪，且给少索引会「成功」但大部分字节不动）。
  P2 解决的正是提交时间。两者互补，不重叠。
- **D4（holder 对称化）会放大这个问题**：更多 client 互为读源，
  意味着更多 client 需要「可读」的注册形态。P2 让「可读」不再等于「原地 strided」，
  因此**P2 是 D4 的前置**，顺序上应当提前。
- **FP8（`fp8_weight_transport.md`）与 P2 正交且互利**：
  FP8 让字节减半、key 数翻倍，于是 descriptor 成本占比**上升**——
  P2 在 FP8 下更重要，而两者的缓冲生命周期规则是同一套。

## 9. 与 verl / miles / vLLM 的对照：为什么它们没遇到这个问题

**它们没遇到，不是因为方案更好，而是因为它们在发送端无条件打平全模型。**
核实源码：

| 框架 | 机制 | 本地拷贝量 | 握手 |
|---|---|---|---|
| **verl** | 512MB 可复用 bucket，`buffer[off:off+n].view(dtype).copy_(weight)`（`bucketed_weight_transfer.py:156`） | **全模型** | 每 bucket 一次 ZMQ 往返 + `synchronize()` |
| **vLLM / SkyRL** | 1GB packed buffer，`.contiguous().view(uint8)` 后 `torch.cat`（`packed_tensor.py:108,132`） | **全模型**（`cat` 还额外分配） | 会话协议 per chunk |
| **miles** | `FlattenedTensorBucket` 按 dtype 打平 | **全模型** | push 语义 |
| **PSRL + P2** | **仅 strided 分片**走落地缓冲，连续分片 RDMA 直写 vLLM 参数 | **2.25 GB / 16 GB = 14%** | **无**（pull，plan 握手期一次编译） |

三条实质差别：

1. **拷贝量少一个量级。** 三家都是「先打平再发」，所以 100% 的权重过一遍拷贝；
   P2 只对**真正 strided** 的分片落地（Qwen3-8B 上是 14%），
   其余 509 个连续分片由 RDMA 直接写进 vLLM 的参数张量，零拷贝。
   **这正是 §3.3「trainer 直供，零额外缓冲」的要求**——
   三家的 bucket 都是约束 (b) 要删的那类常驻缓冲。
2. **没有 push 握手。** verl 每个 bucket 要一次 ZMQ 往返加一次全设备
   `synchronize()`，这在万卡下是 `O(buckets × ranks)` 次同步；
   P2 是 pull，plan 在握手期一次编译，传输期零控制面往返（§3.6「plan once post many」）。
3. **IPC 不跨节点。** verl 的 bucket 走 `reduce_tensor` + CUDA IPC，**只能同节点**；
   vLLM 的 packed 模式同理。P2 走 NIXL RDMA，同节点与跨节点是同一条路径，
   **disaggregate 与 colocate 不需要两套实现**。

**一处必须诚实的地方**：三家的「全模型拷贝」换来的是**它们不需要处理 strided**——
发送端打平之后天然连续。P2 选择性 staging 的代价是**要判断哪些分片需要落地**，
即 `STRIDED_ROW_BUDGET` 与 `must_be_readable` 这两个判定。
这是用一点判定复杂度换 86% 的拷贝量，且判定是**布局的纯函数**（握手期可定），
不是运行时猜测。

## 10. 大 MoE 与万卡：理论分析

### 10.1 大 MoE：收益从「显著」变成「决定性」

DeepSeek-V3 级（`hidden=7168`、61 层、256 experts），gen TP ≠ train TP：

| | 分片数 | descriptor | 提交成本 |
|---|---|---|---|
| 原地 strided | 15,616 | 111,935,488 | **235 s** |
| **P2 staging** | 15,616 | **15,616** | **32.8 ms** |

**7000× 的差距**。原地方案在这个规模上不是「慢」，是**不可用**。

**与 C1（MoE 分组）正交，这一点要说清。** C1 把 256 个 expert 的 `down_proj`
合并成 1 个 key，`row-parallel` 键数从 15,677 降到 122 —— 但
**descriptor 数由 `shard × row` 决定，分片数不变**，所以 C1 不改善这一项。
**C1 治控制面（握手元数据），P2 治数据面（传输提交），两者必须都做。**

### 10.2 万卡：P2 的收益与规模无关，这是它的关键性质

descriptor 成本是**每 client 的本地量**：它只取决于该 client 自己持有多少
strided 分片、每个多少行。因此：

- **P2 的收益不随集群规模衰减**，1024 节点与 1 节点相同；
- **P2 不引入任何跨节点协调**——落地缓冲是进程本地的，scatter 是本地 D2D，
  没有新的屏障、没有新的通知、没有新的 all-to-all；
- 相比之下 verl 的 per-bucket `synchronize()` + ZMQ 往返是
  `O(buckets × ranks)`，**在万卡下是主要的扩展性障碍**。

**扩展性的真实瓶颈在别处，P2 不改变它们**（诚实边界）：
跨节点字节仍受 NIC 限制（实测单 NIC 24.50 GB/s），
所以 §3.5 的去冗余规划、§3.5.3 的 rail 感知选源、FP8 wire 仍然各自必要。
P2 做的是**把一项与规模无关却曾经主导一切的本地成本消掉**，
让那些真正的扩展性工作重新成为瓶颈——这才是它们能被测量和优化的前提。

### 10.3 一处由 P2 实测反推出的带宽更正：扩散的收益比预估小得多

**P2 的实测结果否证了「同节点比跨节点快 14×」这条用于论证扩散的前提。**

实测：0.619s 搬完 gen 每节点 8 client × 8 GB = 64 GB，
即**每节点聚合入口约 103 GB/s**。对比单 NIC 实测 24.50 GB/s，
这意味着**约 4 条 NIC 已在并行工作** —— 单 NIC 的数字不适用于聚合场景。

于是扩散要比较的是 **103 GB/s（跨节点聚合）vs 342.95 GB/s（同节点）= 3.3×**，
而不是 14×。而扩散的成本是实打实的：designate 要多读、要发通知、
要维护落地缓冲的生命周期以供 follower 读。

**这把 S5 从「应该做」改判为「要先证明值得做」**：
P2 之后 653 次读只花 1.4 ms 提交，剩下的全是真实字节；
把 61% 的字节从 103 GB/s 的链路移到 342.95 GB/s 的链路，
理论上限约省 `64×0.61×(1/103 − 1/343) ≈ 0.27s`，
而 designate 要替 follower 多搬这些字节、还要付通知与生命周期开销。
**净收益可能是负的，和扩散在 descriptor 时代的遭遇同构。**

因此 S5 的第一步不是实现，而是**用现有工具量化**。
这条实验不需要写任何新代码，**已经跑完**：

| 配置 | 基线（单相） | 流水 |
|---|---|---|
| **P2：staging + 无扩散** | **0.619 s** | — |
| 扩散 + 原地 strided | 2.519 s | 4.711 s |

**P2 比「扩散 + 原地」快 4.07×。** 两次运行都是 exit=0、16/16 × 399/399。

**结论：S5 不该实现。** 扩散与 staging 互斥，而 staging 侧快 4 倍；
要让扩散追上，它得先付清 descriptor 的账（designate 必须原地注册），
再用 3.3× 的链路差去赢回来 —— 而那 3.3× 最多值 0.27 s，
远不足以覆盖 1.24 s 的提交成本。**这不是实现质量问题，是算术。**

**保留扩散的代码与开关**，因为前提可能变：若将来 gen 侧分片在注册时
就是连续的（§3 的 P1，或 converter 层改造），designate 原地注册只需 1 个
descriptor，扩散的成本项消失、收益项保留，届时 S5 的账会反过来。
`peer_diffusion` 与 `shards_must_be_readable` 让这件事**可测而非可猜**。

### 10.4 一个由 P2 打开的新可能

P2 之前，`chunk_pipeline` 重叠的是 descriptor 提交（不可压缩），
所以流水「正确但无收益」。P2 之后它重叠的是**本地 scatter**（真实工作，
实测 0.023–0.078 ms/分片）与 RDMA —— 两者是不同资源，天然可重叠。
**流水第一次有东西可隐藏**，这是 S5 的前提。
